# Безопасность

Модель угроз, таблица угроз и политика обращения с небезопасными функциями C.
Требования вынесены в `docs/REQUIREMENTS.md`.

## 1. Область защиты

Что защищается:

1. корректность манифеста как снимка каталога;
2. целостность манифеста при передаче по ненадежному каналу;
3. сам процесс от враждебного или испорченного дерева: зависаний, исчерпания
   ресурсов, чтения за пределами переданного корня.

От кого защищаемся:

| Противник | Возможности | Что покрыто |
|---|---|---|
| Пассивный наблюдатель канала | читает трафик | конфиденциальность не требуется: манифест не является секретом |
| Активный противник в канале | изменяет, удаляет, вставляет строки манифеста | HMAC-SHA256 по всем байтам; любое изменение обнаруживается |
| Враждебное дерево | ссылки наружу, каналы FIFO, огромные файлы, необычные имена | `O_NOFOLLOW`, `O_NONBLOCK`, потоковое чтение, побайтовая политика имен |
| Гонка с файловой системой | подмена файла между проверкой и использованием | классификация по `fstat` после открытия и обнаружение изменения файла |
| Другой локальный пользователь | читает `/proc/<pid>/environ` | ключ никогда не передается в аргументах командной строки; остаточный риск описан |

Вне области защиты: компрометация хоста или ядра, враждебная реализация libc,
противник с доступом к файлу ключа, повторное использование старого валидного
манифеста, атаки по побочным каналам на SHA-256.

## 3. Двухшаговая цепочка доверия

HMAC защищает **манифест**, а не файлы. Полная цепочка состоит из двух шагов:

1. `--check`: изменился ли манифест при передаче? Проверяется HMAC с общим ключом.
2. `--verify`: соответствуют ли файлы манифесту? Пересчитывается хэш каждого файла.

Шаги разделены намеренно: при расхождении сразу видно, что именно не сошлось —
подпись или содержимое. Формат отчета:

```
changed: dir_1/file_4
missing: dir_2/file_6.h
added: new_file.txt
ok: 5 entries
```

Код выхода 0 только тогда, когда строк `changed`, `missing` и `added` нет.

## 4. Обращение с ключом

| Источник | Поведение |
|---|---|
| `MANGEN_HMAC_KEY` | используется как есть, без обрезки |
| `--key-file FILE` | отбрасывается один завершающий перевод строки, чтобы работал `echo secret > key` |
| оба источника | ошибка использования, код 2 |
| ни одного источника | ошибка использования, код 2 |
| пустой ключ | ошибка использования, код 2 |
| короче 16 байт | предупреждение, обработка продолжается |

Файл ключа проверяется через `fstat`: если он доступен на запись группе или
остальным, выдается предупреждение (CWE-732). Страницы памяти с ключом блокируются
через `mlock` по возможности: отказ дает предупреждение и не прерывает работу,
поскольку ограничение на блокировку памяти не является ошибкой пользователя. Ключ
зануляется записью через `volatile`, чтобы оптимизатор не удалил запись как мертвую.
Ключ не появляется ни в выводе, ни в сообщениях об ошибках и не принимается в
командной строке, где он был бы виден другим пользователям через `ps`.

## 5. Политика обращения с небезопасными функциями C

Формулировка «использовать безопасные версии функций» имеет в C точный смысл: это
Annex K, интерфейсы с проверкой границ. Этот набор необязателен и в целевой среде
отсутствует.

Замеры на целевой машине:

| Проверка | Результат |
|---|---|
| `__STDC_LIB_EXT1__` в gcc и clang | не определен ни одним компилятором |
| `sprintf_s`, `snprintf_s`, `scanf_s`, `strcpy_s`, `memcpy_s` в `libc.so.6` | отсутствуют (glibc 2.39) |
| `strlcpy`, `strlcat` | есть с glibc 2.38, вне POSIX, требуют `_DEFAULT_SOURCE` |

Поэтому политика строится не на замене опасной функции «безопасным аналогом», а на
устранении класса операций. Три уровня:

| Уровень | Механизм | Что устраняется |
|---|---|---|
| 1. Не использовать | собственные примитивы с явной длиной (`memcpy` с вычисленным размером, строковый буфер) | переполнение и усечение не возникают, потому что нет форматирования в буфер неизвестного размера |
| 2. Где форматирование требуется | `snprintf` со сравнением возвращенного значения с размером буфера | усечение обнаруживается, а не принимается молча |
| 3. Компилятор и анализатор | `_FORTIFY_SOURCE=3`, `-Wformat-security`, `-Wformat-nonliteral`, `clang-analyzer-security.insecureAPI.*` | остаточные случаи ловятся при сборке и во время работы |

### 5.1 Запрещенные функции

| Функция | Причина | Замена |
|---|---|---|
| `strcpy`, `strcat` | нет контроля длины получателя (CWE-120) | `memcpy` с проверенной длиной или `snprintf` |
| `strncpy`, `strncat` | не гарантируют завершающий нуль и легко применяются неверно | `memcpy` с явным добавлением нуля |
| `sprintf`, `vsprintf` | нет параметра размера (CWE-120) | `snprintf`, `vsnprintf` |
| `gets` | ограничения нет вообще, функция удалена из C11 | побайтовое чтение с длиной |
| `scanf`, `fscanf`, `sscanf`, `vscanf` | ширина полей легко забывается; не подходят для враждебного ввода (CWE-676) | собственный побайтовый разбор |
| `alloca` | размер зависит от данных, стек не проверяется | выделение в куче через контекст |
| `mktemp`, `tmpnam` | гонка при создании файла (CWE-377) | `mkstemp` |
| `atoi`, `atol`, `atoll` | нельзя отличить ошибку от нуля | `strtol` с проверкой `errno` и `endptr` |
| данные пользователя в позиции строки формата | подстановка строки формата (CWE-134) | `printf("%s", data)` |

### 5.2 Разрешенные функции и условия

| Функция | Условие |
|---|---|
| `snprintf`, `vsnprintf` | возвращенное значение сравнивается с размером буфера; усечение считается ошибкой, а не нормой |
| `memcpy` | длина вычислена и проверена; области не пересекаются |
| `memmove` | то же, но пересечение допускается |
| `strlen`, `strncmp`, `memcmp`, `strcmp` | работают с уже ограниченными строками; для враждебного ввода используются варианты с длиной |
| `fputs`, `fwrite`, `write` | результат проверяется на ошибку записи |
| `read` в цикле | длина и частичное чтение обрабатываются явно |

### 5.3 Как политика проверяется

| Уровень | Проверка |
|---|---|
| Список запретов | `python3 tools/check_style.py --banned src/ include/ examples/ tests/`: комментарии и строковые литералы вырезаются, иначе `strcpy(` внутри комментария дает ложное срабатывание (измерено) |
| Подавление | маркер `allowlist:` на той же строке или на строке перед вызовом с указанием причины |
| Линтер | `clang-analyzer-security.insecureAPI.*` в наборе `clang-tidy`; проверено, что помечает `strcpy` |
| Формат | `-Wformat=2 -Wformat-security -Wformat-nonliteral` при `-Werror` |
| Во время работы | `_FORTIFY_SOURCE=3` в оптимизированных сборках |
| Модульный тест | `tests/unit/security.cpp::NoUnsafeCalls` сканирует исходники, поэтому правило действует и без оболочки |

### 5.4 Что показали замеры

Буфер 8 байт, вход 20 байт, оба компилятора, оба уровня оптимизации:

| Вариант | gcc | clang |
|---|---|---|
| `sprintf`, `-D_FORTIFY_SOURCE=3`, `-O2` | `*** buffer overflow detected ***`, код 134 | то же |
| `sprintf`, `-D_FORTIFY_SOURCE=3`, `-O0` | `*** stack smashing detected ***`, код 134 | запись прошла, код 0 |
| `sprintf`, без фортификации, `-O2` | `*** stack smashing detected ***`, код 134 | код 139 |
| `snprintf` с размером, любой вариант | усечение до 7 символов, код 0 | то же |

Выводы, учтенные в политике:

1. `snprintf` не переполняет буфер, а усекает. Фортификация здесь бесполезна;
   единственная защита от тихой потери данных — сравнение возвращенного значения с
   размером буфера. Это требование к коду, а не к компилятору.
2. Фортификация защищает именно запрещенные функции, поэтому служит вторым барьером
   на случай обхода запрета. Основным механизмом она не является.
3. Уровень оптимизации имеет значение: при `-O0` в clang защита не работает вовсе
   (измерено), а gcc сообщает иначе. Отладочная сборка слабее оптимизированной.
4. Дистрибутив включает фортификацию только для gcc, поэтому флаг задается явно в
   конфигурации сборки; иначе сборка clang остается без второго барьера.

Ограничение, которое фиксируется открыто: фортификация работает только там, где
размер буфера известен компилятору, и никогда не заменяет проверку длины, когда буфер
приходит через указатель.

## 6. Ограничения, которые не закрываются

| Ограничение | Причина | Возможный следующий шаг |
|---|---|---|
| Повторное использование старого валидного манифеста | в формате нет времени и одноразового значения | добавить отметку времени и окно допустимости |
| Симметричный ключ, нет неотказуемости | HMAC симметричен по определению | асимметричный трейлер |
| `MANGEN_HMAC_KEY` виден в `/proc/<pid>/environ` | свойство переменных окружения | `--key-file` с правами 0600 и `mlock` либо передача ключа через канал |
| Манифест не скрывает имена файлов | формат задан заданием | не требуется |
| Слабый ключ пользователя | HMAC не добавляет энтропию | предупреждение при длине ключа менее 16 байт |
| Побочные каналы на SHA-256 | вне области защиты | — |
| Имена с разделителем или переводом строки не разбираются однозначно | формат задан заданием | ограничение описано в `-h`, в странице руководства и в этом документе |

## 7. Что может запустить проверяющий

```bash
make lint          # clang-tidy: cert-*, bugprone-*, clang-analyzer-security-*
make grep-check    # нет goto, запрещенных функций, процессов, d_type, кириллицы в коде
make test-asan     # ASan + UBSan + LSan
make test          # эталонные векторы, свойства, сквозные сценарии
make demo          # подпись, проверка, порча, сверка
```
